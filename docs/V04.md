# Verdugo Digital v0.4 — lectura verificable y consulta comercial conjunta

## Alcance

Cuatro adaptadores nuevos de lectura: Mautic `contacts.list`, Easy!Appointments `services.list`, Formbricks `surveys.list` y Dub `links.list`. Dos lecturas individuales nuevas: Twenty `people.get` y Chatwoot `contacts.get`. Inventario: 22 adaptadores, 26 acciones HTTP, 6 acciones locales, 14 herramientas MCP y 100 entradas de catálogo. Quedan 78 proyectos sin adaptador y cero proveedores validados en vivo.

El núcleo sigue sin dependencias externas. Esta entrega no instala esos productos ni incorpora todas sus APIs. No automatiza publicaciones, gasto, cobros o envíos. Los ejemplos emplean datos ficticios y no habilitan servicios.

## Una consulta para cuatro superficies

`surface @examples/commercial-surfaces.json` prepara un workflow. Con `--execute`, el motor hace una lectura por servicio seleccionado. Prepara todas las acciones antes de empezar; reutiliza controles, límites, secretos, tenant, auditoría e idempotencia ya existentes. Una fuente no configurada bloquea antes de la primera llamada. Un fallo deja el workflow incompleto; las lecturas completadas no se repiten al usar el mismo ID.

La salida solo resume cantidad de objetos en cada respuesta, clave de ejecución y fecha. No devuelve nombres, emails, destinos de enlaces ni cuerpos completos. Estos sí pueden quedar en el estado local protegido del motor. Una forma de respuesta inválida produce `incomplete` y cantidad nula, nunca un falso cero. Una colección válida vacía produce cero observado.

No suma contactos + servicios + encuestas + enlaces. Ignora totales, ingresos o clics para no inferir pagos. El campo `coverage` siempre declara `single_response_not_complete_export`. No sigue enlaces de paginación ni instrucciones del proveedor. Repetir el ID reutiliza la observación; un nuevo ID produce lecturas frescas.

Límites específicos: Mautic y Easy!Appointments solicitan hasta 50 registros por página; Dub solicita los primeros 50 mediante `pageSize` y no usa su parámetro `page` obsoleto; Formbricks hace una consulta sin paginación inventada y queda sujeta al límite de respuesta de 1 MiB del transporte. No se afirma consistencia de una fotografía común entre proveedores. Easy!Appointments usa una instalación raíz con `/index.php/api/v1/services`, no un subdirectorio arbitrario.

## Readback: separar observación de decisión

El operador identifica un posible ID remoto asociado a una creación `uncertain`. La API de lectura queda fija; no puede indicar una URL, cabecera, otra empresa o un nuevo proveedor. Se exige configuración habilitada y contrato revisado. Las referencias sugeridas por la plantilla son `data.person` para Twenty y `payload` para Chatwoot, pero deben verificarse contra la instancia concreta.

El plan se vincula a la creación original, tenant, ID propuesto, esquema de lectura y fingerprint del GET. La lectura se permite solo con el mismo origen, workspace/cuenta, versión, credencial, política de red y contrato de creación. Chatwoot también mantiene el inbox. Las versiones previas incluyen Content-Type en el hash de cabeceras del POST; v0.4 reconstruye esa firma para comprobar la credencial sin invalidar el historial por comparar GET y POST de forma incorrecta.

La lectura valida ID, email y nombre exactos. Chatwoot exige además que el inbox aparezca asociado. Las discrepancias quedan `mismatch`; errores o formas no compatibles quedan `unverified`. Nada de esto reenvía ni completa la creación. Una lectura concurrente en ejecución devuelve `pending`, no congela la observación como fallo definitivo. Repetir un check no rejuvenece la fecha guardada.

**Coincidir no prueba que el POST original haya creado ese contacto.** Puede ser un contacto preexistente o existir otro duplicado. Tampoco prueba consentimiento. Por ello se exige una revisión humana independiente, con evidencia privada, antes de adoptar el ID. No se usa la coincidencia de email como fusión automática.

## Comandos

1. Inspeccionar `reconciliation-list` para obtener clave y fingerprint de la creación.
2. Preparar un JSON con `key`, `fingerprint`, `remote_id` y un `check_id` nuevo; ejemplo en `examples/contact-readback.json`.
3. Ejecutar `readback @archivo.local.json` y revisar el plan.
4. Ejecutar `readback @archivo.local.json --execute` para realizar el GET.
5. Si devuelve `matched`, revisar el contacto, posibles duplicados y su correspondencia real; no asumir que el matching basta.
6. Preparar este archivo privado y confirmarlo desde un proceso local con rol `approver`:

```json
{
  "check_id": "ID_DE_LA_LECTURA",
  "fingerprint": "FINGERPRINT_DE_READBACK_NO_EL_DE_CREACION",
  "evidence_ref": "REFERENCIA_PRIVADA_A_LA_REVISION_INDEPENDIENTE"
}
```

```bash
python -m verdugo --config verdugo.local.json --role approver --actor local-human reconcile-readback @readback-review.local.json --execute
```

La confirmación no hace red. Comprueba que la observación coincida, no tenga más de 300 segundos, no haya cambiado su esquema/configuración y conserve el resultado almacenado. La creación debe seguir `uncertain`. Un contacto ya vinculado a otra creación no se reasigna. El registro de conciliación, cierre y auditoría son atómicos; dos aprobadores no pueden aplicarlo dos veces.

Para continuar un trabajo bloqueado: `job-resume JOB_ID --execute` y luego `worker --execute`, siempre que tenga intentos restantes y las otras aprobaciones sigan vigentes. Las aprobaciones caducadas deben renovarse sobre los mismos planes, nunca borrar claves. Un workflow invocado directamente se reanuda repitiendo su orden original.

El resultado de creación se reconstruye mínimamente con el ID comprobado para permitir el vínculo existente. **No se presenta como la respuesta original del POST.** La auditoría identifica `provider_readback_plus_human_review`, el GET y su hash; mantiene `creation_proven: false`. La conciliación humana anterior sigue disponible, con su semántica menos fuerte y diferenciada.

## Evidencia de esta entrega

Fecha: 2026-11-11. Python local 3.13.5. Baseline v0.3: 166 pruebas aprobadas y árbol `083a47adb9a45c0cbdb3ab80de348f3a06e43407` coincidente con GitHub. Suite v0.4: 221 pruebas, cero fallos; 55 pruebas nuevas. Se comprobaron compilación, demo sintética, inventario y compatibilidad de fingerprints v0.3. El resultado de GitHub Actions se consulta por commit, no se deduce de esta prueba local.

Pruebas nuevas incluyen cuatro rutas HTTP locales de lectura, resumen conjunto sin inferir dinero, esquemas inválidos, paginación no implementada, restricciones de argumentos, preflight completo, aislamiento de tenants y replay persistente. Readback prueba coincidencias/desacuerdos, ámbito/cuenta/inbox/credencial/versión, caducidad, esquema, lectura concurrente, confirmación concurrente y rollback de evidencia.

Recorrido completo probado: evento canónico firmado → cola → aprobación del puente → POST Twenty con respuesta incierta → GET de comprobación → revisión separada → reanudación → POST Chatwoot → dos vínculos. Todos los proveedores de esa prueba son servidores HTTP loopback sintéticos; el POST inicial no se repite.

No son auditorías exhaustivas ni pruebas de los servicios reales. Ningún servicio se marca `live_verified` por devolver HTTP 200. No hay datos comerciales, credenciales reales, aceptación de licencias, gasto ni mensajería a terceros en estas pruebas.

## Pendiente prioritario

Persisten la recuperación de `running` con fencing verificable, ingreso productivo y firmas nativas, IAM, supervisor/heartbeat, retención/backup/restauración, cuotas totales y pruebas de carga. No hay sincronización bidireccional. La comprobación de contacto requiere un ID candidato y no busca todos los posibles duplicados. Cambiar credenciales o versiones requiere un procedimiento de migración/revisión; esta versión bloquea antes de mezclar contextos.

Para producción se necesitan instancias autorizadas y contratos/ediciones/versiones concretos. Las demás 78 integraciones necesitan adaptadores apropiados; algunas son bibliotecas o herramientas de CI, no APIs HTTP. No habilitarlas únicamente para aumentar un contador.
