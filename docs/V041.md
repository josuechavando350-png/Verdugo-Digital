# Verdugo Digital v0.4.1 — recuperación local con exclusión de ejecución

Esta entrega parte del commit `90c5319f78fe7e88bc2420f90021351e84ef8ef4`. Conserva los cuatro adaptadores y la comprobación remota añadidos en v0.4: **22 adaptadores HTTP, 26 acciones externas, 14 herramientas MCP y cero proveedores validados en vivo**. No incorpora otro mecanismo de lectura remota ni otra aprobación: reutiliza `readback` de v0.4.

## Problema resuelto

Una creación puede quedar `running` si el proceso muere después de comenzar el envío. Antes solo podía mantenerse bloqueada. No es correcto declararla fallida o repetirla porque pasó un plazo: el proveedor puede haberla aplicado.

Cada ejecución nueva mantiene un bloqueo cooperativo exclusivo por empresa/clave durante la llamada y su cierre. El marcador `run_guards` se inserta en la misma transacción que `runs`. Un aprobador solo puede convertir `running` en `uncertain` cuando consigue ese mismo bloqueo, encuentra el marcador compatible y verifica el plan exacto.

**No autoriza reenvíos ni declara éxito.** Después se utiliza la lectura de comprobación y revisión separada de v0.4. El proveedor aún puede estar procesando una petición aunque el proceso local haya terminado. Una lectura coincidente no demuestra el origen de la creación ni descarta duplicados.

## Uso

Consultar `reconciliation-list` y preparar un archivo privado con `key` y `fingerprint` exactos. No incluir secretos.

```bash
python -m verdugo --config verdugo.local.json --role approver recover-running @recovery.local.json
python -m verdugo --config verdugo.local.json --role approver recover-running @recovery.local.json --execute
```

El primer comando solo comprueba y no cambia la ejecución. El segundo deja el resultado `uncertain`, con salida CLI 1 porque sigue incompleto. Si el proceso continúa reteniendo el bloqueo, ambos se rechazan. El MCP no puede ejecutar esta transición ni aprobarla; conserva sus 14 herramientas. Las respuestas `running` ahora se marcan como incompletas en CLI/MCP.

Seguir el procedimiento `readback`/`reconcile-readback` de [v0.4](V04.md). Luego reanudar el trabajo o flujo con sus mismas claves, sin borrar ejecuciones, identidades, aprobaciones ni presupuestos de intentos. La caducidad de la asignación del trabajo y la conciliación de la acción son controles diferentes.

## Corrección de SQLite

Se eliminó el `os.open`/`os.close` de la base antes de `sqlite3.connect`. Abrir y cerrar un descriptor ajeno al gestor SQLite puede cancelar bloqueos POSIX de otras conexiones del proceso. Ahora SQLite gestiona sus propios descriptores. El directorio del estado debe pertenecer al usuario del proceso y tener modo 0700; la base se protege con 0600. Se rechazan archivos no regulares y enlaces duros. Un alias simbólico se resuelve a la misma ruta canónica.

La prueba de regresión abre/cierra conexiones hermanas, alterna escrituras de procesos padre/hijo y comprueba visibilidad e integridad. El endurecimiento no se presenta como auditoría exhaustiva ni certificación de producción.

## Alcance y actualización

Solo para un host confiable, sistema de archivos local y ejecución cooperativa POSIX con `flock`. No usar NFS, volúmenes compartidos entre hosts, procesos que ignoren los bloqueos ni cambios de base en caliente. No se usan PIDs ni un timeout como prueba de ausencia de efectos. No matar procesos productivos automáticamente.

Detener todos los procesos de versiones anteriores y respaldar coherentemente el estado antes de actualizar. No mezclar trabajadores v0.3/v0.4 con esta versión sobre la misma base. La migración añade una tabla sin borrar datos. Los `running` antiguos sin marcador, bases copiadas/restauradas con otro ámbito de ruta/dispositivo/inodo y estado en memoria **no son recuperables por este comando**: requieren revisión fuera de línea. Esto es deliberado, no un permiso para borrar marcas o cambiar claves.

Los archivos de bloqueo no se eliminan al liberar; borrar un archivo retenido podría permitir dos dueños sobre inodos diferentes. Se necesita política de retención offline; no se entrega limpieza automática. Los roles siguen siendo locales, no IAM; un administrador del host puede modificar archivos y base.

## Evidencia de esta entrega

Se añadieron **24 pruebas**. Incluyen un subproceso real que retiene la ejecución: la recuperación falla mientras está activo y solo avanza a `uncertain` tras finalizarlo en la prueba. Se prueban atomicidad, ámbito de empresa/archivo, planes alterados, estados antiguos, archivos privados, ausencia de autoaprobación MCP y una cadena de cola → interrupción → recuperación → lectura remota sintética → revisión → continuación sin repetir el primer POST.

Validación local: 24 pruebas nuevas y 166 pruebas previas disponibles, con expectativas de inventario ajustadas a v0.4, **190 aprobadas**, más compilación y demo sintética. Las 55 pruebas añadidas por la actualización concurrente v0.4 se conservan intactas en GitHub y deben ejecutarse mediante CI junto con estas 24; no se afirma aquí haberlas ejecutado localmente. El resultado integral de CI se informa por commit en el PR, no se infiere del resultado local.

No se desplegaron servicios, no se conectó este chat al MCP, no se enviaron campañas ni se gastó presupuesto. El catálogo permanece en 100 proyectos; 78 aún no tienen adaptador. No hay evidencia nueva de ingresos ni de una probabilidad comercial del 90%.
