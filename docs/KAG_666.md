# KAG: estado de una tarea existente

`kag / task.summary` incorpora la consulta del Solver Server de OpenSPG/KAG al
mismo Engine, doctor, product-run, CLI/MCP y SQLite. Usa la identidad ya
registrada; no añade otro repositorio ni cuenta una segunda pieza con otro nombre.

El contrato proviene del commit
`fdab15b3929d2ee40dfcdd388f90233096a6afc9`. La licencia raíz Apache-2.0 se
conserva en `sources/license-texts/`; las rutas, blobs Git y SHA256 del servidor,
los modelos de petición y la caché están en `sources/contracts-task-reads666.json`.

## Operación

El operador configura privadamente el UUID4 de una tarea existente mediante una
variable `VERDUGO_*`. El motor envía un único `POST /process`, con el formato
original `features.in_string`: una cadena JSON con `cmd=query`, el identificador,
`app_id=0`, `project_id=0`, `req="{}"` y `config="{}"`. El servidor consultado usa
solo `req_id` en esa rama. No se admiten parámetros de usuario para cambiar el
destino, la tarea, el comando, el modelo, la consulta o un callback.

La respuesta debe corresponder al UUID solicitado. El resultado conservado
contiene un recuento para `running`, `completed` o `failed`, sin identificador,
respuesta del solver ni mensaje de error original. La caché original devuelve
`failed` tanto cuando falta o expiró el resultado como cuando falló una tarea;
el informe conserva esa ambigüedad. `completed` no certifica calidad del
resultado, veracidad ni éxito comercial.

El UUID solo entra al cuerpo privado de esta operación. Un digest liga la
petición al plan y a la respuesta. La función que construye el cuerpo acepta
exclusivamente este contrato; no es un mecanismo genérico para sobrescribir
peticiones. Cambiar tarea, credencial o controles invalida la reutilización del
mismo identificador de ejecución. El replay conserva la observación anterior;
una nueva consulta requiere un nuevo ID de ejecución.

## Configuración deshabilitada por defecto

La ruta original no contiene autenticación. Se exige una instancia dedicada y
un proxy autenticador revisado por el operador, que retire la credencial antes
de reenviar al servidor. El encabezado Bearer pertenece al proxy; no se presenta
como autenticación nativa de KAG. Estos controles empiezan en `false`:

- `proxy_auth_reviewed`
- `proxy_strips_credentials_reviewed`
- `dedicated_instance_reviewed`
- `task_scope_reviewed`

La superficie es `self_hosted_solver_server`, el modo
`reviewed_proxy_bearer` y `task_id_env` debe apuntar a la variable privada de la
tarea. También se exige `enabled`, `license_reviewed`, versión explícita y la
credencial por empresa. Programar este conector no habilita una instalación.

## Evidencia y límites

Pasaron 11 pruebas del nuevo contrato: formato original, controles deshabilitados,
parámetros prohibidos, UUID, correlación, respuestas inválidas, errores HTTP,
límites de tamaño, privacidad, CLI/MCP, product-run y replay después de reiniciar
SQLite. El conjunto del proyecto pasó 915 pruebas. El flujo sintético conjunto
incluye 78 observaciones HTTP y la instantánea comercial local.

`tests_runtime/accept_task_source666.py` prepara y verifica dos archivos originales
sin modificarlos. Con el perfil de pruebas Langroid existente ejecuta el modelo
original de petición y la caché original con cinco casos: en curso, completado,
fallido, ausente y expirado. No carga `SolverMain`, no somete tareas, no llama
modelos y no ejecuta el despacho HTTP o el servidor completo. Los sockets del
conector usan respuestas sintéticas. La aceptación CI ejecuta esa prueba parcial
con aislamiento de red del sistema operativo; su resultado debe observarse en
el commit correspondiente.

El cierre de dependencias de un despliegue completo, los pesos y la instalación
productiva permanecen pendientes. La evidencia local está en
`evidence/accepted/kag-original-boundary-local-20261115.json`; no se atribuye
aislamiento de red del sistema operativo a esa ejecución local.
